# Пользовательские сценарии (Use Cases) сервиса Tasker

## Введение

Данный документ содержит детальное описание всех пользовательских сценариев (Use Cases) системы Tasker. Каждый сценарий описывает конкретное взаимодействие между актором и системой.

**Версия документа:** 1.0  
**Дата:** 25 января 2026 г.

---

## Акторы системы

### Первичные акторы

#### Пользователь (User)
**Описание:** Конечный пользователь системы Personage, для которого система автоматически создает задачи на основе событий из различных источников.

**Права:**
- Просмотр своих задач (в будущем)
- Обновление статуса задач (в будущем)
- Планирование задач (в будущем)

**Ответственность:**
- Подключает внешние коннекторы (Gmail, Telegram, Google Calendar)
- Взаимодействует с внешними системами, генерирующими события

---

### Внешние системы

#### Внешний коннектор (Connector)
**Описание:** Система-адаптер, которая интегрируется с внешними сервисами (Gmail, Telegram, Google Calendar) и преобразует их события в формат Protobuf для публикации в SQS.

**Типы коннекторов:**
- Gmail Connector
- Telegram Connector
- Google Calendar Connector

**Ответственность:**
- Получение событий из внешних источников
- Преобразование в Protobuf формат (eventsPb.Event)
- Публикация в Yandex Message Queue (SQS)

---

### Внутренние компоненты (Системные акторы)

#### SQS Worker
**Описание:** Фоновый процесс, который опрашивает SQS очередь и обрабатывает входящие события.

**Параметры:**
- Интервал опроса: 1 секунда
- Параллельных обработчиков: 5
- Таймаут обработки: 10 секунд

**Ответственность:**
- Получение событий из очереди
- Нормализация контекста
- Генерация embeddings
- Кластеризация событий

---

#### Cluster Closure Worker
**Описание:** Фоновый процесс, который периодически проверяет и закрывает кластеры, готовые к генерации задач.

**Параметры:**
- Интервал проверки: 5 секунд
- Размер батча: 10 кластеров
- Max event count: 5
- Inactivity timeout: 5 минут

**Ответственность:**
- Поиск кластеров, готовых к закрытию
- Генерация задач через LLM
- Управление жизненным циклом кластеров

---

### Внешние сервисы

#### LLM Service (OpenRouter)
**Описание:** Внешний API для доступа к большим языковым моделям.

**Модель:** xiaomi/mimo-v2-flash:free

**Ответственность:**
- Анализ событий кластера
- Генерация actionable задач
- Возврат структурированного JSON

---

#### Embedding Service (OpenAI)
**Описание:** Внешний API для генерации векторных представлений текста.

**Модель:** openai/text-embedding-3-small

**Ответственность:**
- Генерация 1536-мерных векторов из текста
- Обеспечение семантического поиска

---

## Use Cases: Обработка событий

### UC-1: Получить событие из очереди

**ID:** UC-1  
**Название:** Получить событие из очереди  
**Актор:** SQS Worker  
**Описание:** Система получает событие от внешнего коннектора через SQS очередь.

#### Предусловия
- SQS Worker запущен и работает
- Очередь connector-events.fifo настроена
- Коннектор опубликовал событие в очередь

#### Основной поток
1. SQS Worker опрашивает очередь каждую секунду
2. Система получает сообщение в формате Protobuf (eventsPb.Event)
3. Система десериализует Protobuf в структуру
4. Система валидирует обязательные поля (ID, UserID, ConnectorType)
5. Переход к UC-2

#### Альтернативные потоки
**A1: Очередь пуста**
- Система ожидает следующей итерации опроса
- Возврат к шагу 1

**A2: Ошибка десериализации**
- Система логирует ошибку
- Сообщение удаляется из очереди (corrupted)
- Возврат к шагу 1

**A3: Таймаут обработки (10 сек)**
- Сообщение возвращается в очередь
- Повторная попытка обработки

#### Постусловия
- Событие получено и готово к нормализации

#### Нефункциональные требования
- Пропускная способность: до 5 событий параллельно
- Latency: < 100ms на получение сообщения

---

### UC-2: Нормализовать контекст события

**ID:** UC-2  
**Название:** Нормализовать контекст события  
**Актор:** SQS Worker  
**Описание:** Преобразование Protobuf контекста в унифицированный текстовый формат.

#### Предусловия
- Событие получено из очереди (UC-1)
- Protobuf структура валидна

#### Основной поток
1. Система извлекает поля из eventsPb.Event.Context
2. Система форматирует участников:
   - Извлекает email, name, telegram_tag
   - Сортирует участников (для детерминированности)
3. Система форматирует временные метки в RFC3339
4. Система создает нормализованный контекст по шаблону:
   ```
   SOURCE: <источник>
   SUBJECT: <тема>
   WHEN: <время в RFC3339>
   SENDER: [EMAIL <email> NAME <имя> TELEGRAM_TAG <тег>]
   PARTICIPANTS: [EMAIL <email> NAME <имя> TELEGRAM_TAG <тег>], ...
   START TIME: <время начала в RFC3339>
   END TIME: <время окончания в RFC3339>
   TEXT:
   <текст сообщения>
   ```
5. Система создает доменный объект Event
6. Переход к UC-3

#### Альтернативные потоки
**A1: Опциональные поля отсутствуют**
- Система вставляет пустые строки
- Продолжение основного потока

#### Постусловия
- Создан объект Event с NormalizedEventContext
- Контекст готов для генерации embedding

#### Нефункциональные требования
- Время обработки: < 10ms
- Детерминированность: один и тот же Protobuf → один и тот же текст

---

### UC-3: Сгенерировать embedding

**ID:** UC-3  
**Название:** Сгенерировать embedding  
**Актор:** SQS Worker  
**Внешний сервис:** Embedding API (OpenAI)  
**Описание:** Генерация векторного представления события для семантического поиска.

#### Предусловия
- Событие нормализовано (UC-2)
- NormalizedEventContext не пустой
- Embedding API доступен

#### Основной поток
1. Система подготавливает запрос к Embedding API:
   - Вход: [NormalizedEventContext]
   - Модель: openai/text-embedding-3-small
2. Система отправляет запрос через OpenRouter
3. Система получает ответ с вектором размерности 1536
4. Система преобразует float64 → float32
5. Система создает EventWithEmbedding
6. Переход к UC-4

#### Альтернативные потоки
**A1: Ошибка API (timeout, rate limit)**
- Система ждет экспоненциальный backoff
- Повторная попытка (до 3 раз)
- Если все попытки неудачны → логирование ошибки, возврат в очередь

**A2: Невалидный ответ API**
- Система логирует ошибку
- Возврат в очередь для повторной обработки

#### Постусловия
- Создан EventWithEmbedding с вектором 1536 измерений
- Готов для кластеризации

#### Нефункциональные требования
- Таймаут: 30 секунд
- Retry policy: экспоненциальный backoff (1s, 2s, 4s)

## Use Cases: Кластеризация

### UC-4: Найти похожие кластеры

**ID:** UC-4  
**Название:** Найти похожие кластеры  
**Актор:** SQS Worker  
**Описание:** Поиск top-K наиболее похожих открытых кластеров пользователя.

#### Предусловия
- EventWithEmbedding создан (UC-3)
- База данных доступна
- Расширение pgvector установлено

#### Основной поток
1. Система формирует запрос поиска:
   - UserID из события
   - Embedding вектор
   - TopK = 5
   - Статус = "open"
2. Система выполняет векторный поиск в PostgreSQL:
   ```sql
   SELECT *, 1 - (centroid <=> $embedding) as similarity
   FROM clusters
   WHERE user_id = $userID AND status = 'open'
   ORDER BY centroid <=> $embedding
   LIMIT 5
   ```
3. Система получает список ClusterWithSimilarity
4. Система сортирует по убыванию similarity
5. Если список пустой → переход к UC-6
6. Если similarity[0] >= 0.6 → переход к UC-5
7. Иначе → переход к UC-6

#### Альтернативные потоки
**A1: Нет кластеров для пользователя**
- Возврат пустого списка
- Переход к UC-6

**A2: Ошибка БД**
- Логирование ошибки
- Повторная попытка запроса
- Если не удалось → возврат события в очередь

#### Постусловия
- Получен список похожих кластеров с метриками similarity
- Принято решение: присоединить или создать новый

#### Нефункциональные требования
- Время запроса: < 100ms (благодаря HNSW индексу)
- Точность HNSW: recall >= 0.95

---

### UC-5: Присоединить событие к кластеру

**ID:** UC-5  
**Название:** Присоединить событие к существующему кластеру  
**Актор:** SQS Worker  
**Описание:** Добавление события в существующий кластер с обновлением центроида.

#### Предусловия
- Найден похожий кластер (UC-4)
- Similarity >= 0.6
- Кластер имеет статус "open"

#### Основной поток
1. Система выбирает кластер с максимальной similarity
2. Система присваивает event.ClusterID = cluster.ID
3. Переход к UC-7 (обновление центроида)

#### Альтернативные потоки
Нет

#### Постусловия
- Событие ассоциировано с существующим кластером
- Готово к обновлению центроида

---

### UC-6: Создать новый кластер

**ID:** UC-6  
**Название:** Создать новый кластер  
**Актор:** SQS Worker  
**Описание:** Создание нового кластера, когда не найдено подходящих существующих.

#### Предусловия
- Не найдено похожих кластеров ИЛИ similarity < 0.6 (UC-4)

#### Основной поток
1. Система генерирует UUID для ClusterID
2. Система создает новый Cluster:
   - ID = UUID
   - UserID из события
   - Centroid = event.Embedding
   - EventCount = 1
   - Status = "open"
   - CreatedAt = now()
   - UpdatedAt = now()
3. Система присваивает event.ClusterID = cluster.ID
4. Переход к UC-8

#### Альтернативные потоки
Нет

#### Постусловия
- Создан новый кластер со статусом "open"
- Событие ассоциировано с новым кластером
- EventCount = 1

---

### UC-7: Обновить центроид кластера

**ID:** UC-7  
**Название:** Обновить центроид кластера  
**Актор:** SQS Worker  
**Описание:** Пересчет центроида кластера при добавлении нового события.

#### Предусловия
- Событие присоединено к существующему кластеру (UC-5)
- Кластер загружен из БД

#### Основной поток
1. Система получает текущие значения:
   - n = cluster.EventCount
   - old_centroid = cluster.Centroid
   - event_embedding = event.Embedding
2. Система вычисляет новый центроид по формуле инкрементального среднего:
   ```
   Для каждой компоненты i (от 0 до 1535):
     new_centroid[i] = (old_centroid[i] * n + event_embedding[i]) / (n + 1)
   ```
3. Система обновляет кластер:
   - cluster.Centroid = new_centroid
   - cluster.EventCount = n + 1
   - cluster.UpdatedAt = now()
4. Переход к UC-8

#### Альтернативные потоки
Нет

#### Постусловия
- Центроид кластера обновлен
- EventCount увеличен на 1
- UpdatedAt обновлен

#### Нефункциональные требования
- Время вычисления: < 1ms (1536 операций)
- Точность: float32

---

### UC-8: Сохранить событие и кластер

**ID:** UC-8  
**Название:** Сохранить событие и кластер в БД  
**Актор:** SQS Worker  
**Описание:** Атомарное сохранение обновленного кластера и события в транзакции.

#### Предусловия
- Кластер создан или обновлен (UC-6 или UC-7)
- Событие ассоциировано с кластером
- База данных доступна

#### Основной поток
1. Система начинает транзакцию (Isolation: READ COMMITTED)
2. Система выполняет UPSERT кластера:
   ```sql
   INSERT INTO clusters (cluster_id, user_id, centroid, event_count, status, ...)
   VALUES (...)
   ON CONFLICT (cluster_id) DO UPDATE SET
     centroid = EXCLUDED.centroid,
     event_count = EXCLUDED.event_count,
     updated_at = EXCLUDED.updated_at
   ```
3. Система выполняет UPSERT события:
   ```sql
   INSERT INTO events (event_id, user_id, source, context, embedding, cluster_id, ...)
   VALUES (...)
   ON CONFLICT (event_id) DO UPDATE SET
     cluster_id = EXCLUDED.cluster_id,
     ...
   ```
4. Система коммитит транзакцию
5. Система удаляет сообщение из SQS очереди
6. Система логирует успех

#### Альтернативные потоки
**A1: Ошибка транзакции**
- Система откатывает транзакцию
- Логирование ошибки
- Сообщение остается в очереди
- Повторная обработка после visibility timeout

**A2: Constraint violation**
- Rollback транзакции
- Логирование ошибки
- Анализ причины (duplicate event_id, invalid foreign key)

#### Постусловия
- Кластер и событие сохранены в БД
- Транзакция зафиксирована
- Сообщение удалено из очереди
- Система готова к обработке следующего события

#### Нефункциональные требования
- Atomicity: обе операции либо успешны, либо откачены
- Isolation: READ COMMITTED
- Время выполнения: < 50ms

## Use Cases: Управление жизненным циклом кластеров

### UC-9: Найти кластеры готовые к закрытию

**ID:** UC-9  
**Название:** Найти кластеры готовые к закрытию  
**Актор:** Cluster Closure Worker  
**Описание:** Периодический поиск кластеров, достигших критериев закрытия.

#### Предусловия
- Cluster Closure Worker запущен
- База данных доступна
- Есть открытые кластеры

#### Основной поток
1. Worker просыпается каждые 5 секунд
2. Система вычисляет порог неактивности:
   ```
   inactivity_threshold = now() - 5 minutes
   ```
3. Система выполняет запрос с блокировкой:
   ```sql
   SELECT *
   FROM clusters
   WHERE status = 'open'
     AND (event_count >= 5 OR updated_at < $inactivity_threshold)
   ORDER BY updated_at ASC
   LIMIT 10
   FOR UPDATE SKIP LOCKED
   ```
4. Система получает батч кластеров (до 10 штук)
5. Если батч пустой → завершение, ожидание следующей итерации
6. Для каждого кластера → переход к UC-10

#### Альтернативные потоки
**A1: Нет кластеров для закрытия**
- Система логирует "no clusters to close"
- Ожидание следующей итерации

**A2: Ошибка БД**
- Логирование ошибки
- Ожидание следующей итерации

#### Постусловия
- Получен батч кластеров, заблокированных для обработки
- Другие воркеры не могут обработать эти же кластеры

#### Нефункциональные требования
- Интервал: 5 секунд
- Размер батча: 10
- Блокировка: SKIP LOCKED (для multi-instance deployment)

---

### UC-10: Перевести кластер в статус Processing

**ID:** UC-10  
**Название:** Перевести кластер в статус Processing  
**Актор:** Cluster Closure Worker  
**Описание:** Изменение статуса кластера перед генерацией задачи.

#### Предусловия
- Кластер найден и заблокирован (UC-9)
- Статус кластера = "open"

#### Основной поток
1. Система обновляет статус кластера:
   ```sql
   UPDATE clusters
   SET status = 'processing', updated_at = now()
   WHERE cluster_id = $clusterID
   ```
2. Система логирует переход статуса
3. Переход к UC-11

#### Альтернативные потоки
**A1: Ошибка обновления**
- Логирование ошибки
- Пропуск кластера
- Обработка следующего кластера из батча

#### Постусловия
- Статус кластера = "processing"
- Кластер не будет обработан повторно
- Новые события не будут добавлены в этот кластер

---

### UC-11: Получить события кластера

**ID:** UC-11  
**Название:** Получить события кластера  
**Актор:** Cluster Closure Worker  
**Описание:** Загрузка всех событий кластера для генерации задачи.

#### Предусловия
- Кластер переведен в статус "processing" (UC-10)

#### Основной поток
1. Система выполняет запрос:
   ```sql
   SELECT event_id, user_id, source, occurred_at, context, cluster_id
   FROM events
   WHERE cluster_id = $clusterID
   ORDER BY occurred_at ASC
   ```
2. Система получает список событий (без embeddings)
3. Если список пустой → переход к UC-14 (закрытие без задачи)
4. Иначе → переход к UC-12

#### Альтернативные потоки
**A1: Ошибка запроса**
- Логирование ошибки
- Переход к UC-15 (откат статуса)

**A2: Пустой кластер**
- Логирование "empty cluster"
- Переход к UC-14 (закрытие без создания задачи)

#### Постусловия
- Загружены все события кластера
- События отсортированы по времени возникновения
- Готов список для передачи в LLM

#### Нефункциональные требования
- Время запроса: < 50ms
- Сортировка по occurred_at ASC

## Use Cases: Генерация задач

### UC-12: Сгенерировать задачу через LLM

**ID:** UC-12  
**Название:** Сгенерировать задачу через LLM  
**Актор:** Cluster Closure Worker  
**Внешний сервис:** LLM Service (OpenRouter)  
**Описание:** Анализ событий кластера и генерация actionable задачи.

#### Предусловия
- Получены события кластера (UC-11)
- Список событий не пуст
- LLM API доступен

#### Основной поток
1. Система форматирует события для LLM:
   ```
   --- Event 1 ---
   <NormalizedEventContext>
   
   --- Event 2 ---
   <NormalizedEventContext>
   ...
   ```
2. Система создает промпт на основе шаблона:
   - System: инструкции для извлечения задачи
   - User: форматированные события
3. Система отправляет запрос к LLM:
   - Модель: xiaomi/mimo-v2-flash:free
   - Таймаут: 30 секунд
4. Система получает ответ LLM
5. Система извлекает JSON из ответа (обработка markdown блоков)
6. Система парсит JSON в структуру GeneratedTask:
   ```json
   {
     "title": "string",
     "description": "string",
     "duration_minutes": number,
     "priority": number,
     "deadline": "ISO8601 or null",
     "start_time": "ISO8601 or null"
   }
   ```
7. Система парсит даты из ISO8601 в time.Time
8. Переход к UC-13

#### Альтернативные потоки
**A1: Timeout LLM (30 сек)**
- Логирование ошибки
- Переход к UC-15 (откат статуса кластера)

**A2: Невалидный JSON в ответе**
- Попытка извлечь JSON из markdown блоков
- Если не удалось → логирование, переход к UC-15

**A3: Rate limit API**
- Ожидание согласно Retry-After header
- Повторная попытка
- Если превышено 3 попытки → переход к UC-15

**A4: Некорректная структура JSON**
- Логирование ошибки и полученного JSON
- Переход к UC-15

#### Постусловия
- Создан объект GeneratedTask
- Все поля валидированы
- Готов для сохранения в БД

#### Нефункциональные требования
- Таймаут: 30 секунд
- Retry: до 3 попыток при rate limit
- Формат: JSON

#### Примеры ответа LLM
**Успешный:**
```json
{
  "title": "Review Q4 budget proposal",
  "description": "Review the budget proposal sent by Finance team and provide feedback",
  "duration_minutes": 45,
  "priority": 7,
  "deadline": "2026-02-01T18:00:00Z",
  "start_time": null
```

### UC-13: Создать задачу в БД

**ID:** UC-13  
**Название:** Создать задачу в БД  
**Актор:** Cluster Closure Worker  
**Описание:** Сохранение сгенерированной задачи в базе данных.

#### Предусловия
- Задача сгенерирована LLM (UC-12)
- GeneratedTask валиден
- База данных доступна

#### Основной поток
1. Система создает доменный объект Task:
   ```go
   Task{
     ID:          UUID(),
     UserID:      cluster.UserID,
     ClusterID:   cluster.ID,
     Title:       generatedTask.Title,
     Description: generatedTask.Description,
     Duration:    time.Duration(generatedTask.DurationMinutes) * time.Minute,
     Priority:    generatedTask.Priority,
     Deadline:    generatedTask.Deadline,
     StartTime:   generatedTask.StartTime,
     Status:      TaskStatusPending,
     CreatedAt:   now(),
     UpdatedAt:   now(),
   }
   ```
2. Система выполняет INSERT:
   ```sql
   INSERT INTO tasks (task_id, user_id, cluster_id, title, description, ...)
   VALUES (...)
   ```
3. Система проверяет успешность вставки
4. Переход к UC-14

#### Альтернативные потоки
**A1: Нарушение UNIQUE constraint (cluster_id)**
- Логирование предупреждения (кластер уже имеет задачу)
- Переход к UC-14 (считаем успехом)

**A2: Ошибка INSERT**
- Логирование ошибки
- Переход к UC-15 (откат статуса кластера)

#### Постусловия
- Задача сохранена в БД
- Задача имеет статус "pending"
- Связь Task.ClusterID → Cluster.ID установлена

#### Нефункциональные требования
- Время выполнения: < 20ms
- UNIQUE constraint на cluster_id

### UC-14: Закрыть кластер

**ID:** UC-14  
**Название:** Закрыть кластер  
**Актор:** Cluster Closure Worker  
**Описание:** Финальный перевод кластера в статус "closed".

#### Предусловия
- Задача создана в БД (UC-13) ИЛИ кластер пуст (UC-11, A2)
- Кластер имеет статус "processing"

#### Основной поток
1. Система обновляет статус кластера:
   ```sql
   UPDATE clusters
   SET status = 'closed', updated_at = now()
   WHERE cluster_id = $clusterID
   ```
2. Система логирует успешное закрытие кластера
3. Система переходит к обработке следующего кластера из батча

#### Альтернативные потоки
**A1: Ошибка обновления**
- Логирование ошибки
- Кластер остается в статусе "processing"
- Потребуется ручное вмешательство

#### Постусловия
- Статус кластера = "closed"
- Кластер больше не будет обрабатываться
- Новые события не будут добавлены
- Задача создана (если кластер не был пуст)

### UC-15: Откатить статус при ошибке

**ID:** UC-15  
**Название:** Откатить статус кластера при ошибке  
**Актор:** Cluster Closure Worker  
**Описание:** Возврат кластера в статус "open" при ошибке генерации или сохранения задачи.

#### Предусловия
- Произошла ошибка в UC-12 или UC-13
- Кластер имеет статус "processing"

#### Основной поток
1. Система логирует причину ошибки
2. Система обновляет статус кластера:
   ```sql
   UPDATE clusters
   SET status = 'open', updated_at = now()
   WHERE cluster_id = $clusterID
   ```
3. Система логирует откат статуса
4. Система переходит к обработке следующего кластера

#### Альтернативные потоки
**A1: Ошибка отката**
- Логирование критической ошибки
- Кластер остается в статусе "processing"
- Алерт для администратора

#### Постусловия
- Статус кластера = "open"
- Кластер будет повторно обработан в следующей итерации
- Сохранена возможность добавления новых событий

#### Нефункциональные требования
- Обязательное логирование причины отката
- Мониторинг частоты откатов

## Диаграмма последовательности: Полный цикл обработки события

```
Connector -> SQS: Publish Event (Protobuf)
SQS -> SQS Worker: Poll message (1s interval)
SQS Worker -> SQS Worker: UC-1: Get event
SQS Worker -> SQS Worker: UC-2: Normalize context
SQS Worker -> Embedding API: UC-3: Generate embedding
Embedding API -> SQS Worker: Return vector(1536)
SQS Worker -> PostgreSQL: UC-4: Find similar clusters
PostgreSQL -> SQS Worker: Return top-5 clusters
alt similarity >= 0.6
    SQS Worker -> SQS Worker: UC-5: Join existing cluster
    SQS Worker -> SQS Worker: UC-7: Update centroid
else similarity < 0.6
    SQS Worker -> SQS Worker: UC-6: Create new cluster
end
SQS Worker -> PostgreSQL: UC-8: Save cluster & event (TX)
PostgreSQL -> SQS Worker: Commit successful
SQS Worker -> SQS: Delete message
```

## Диаграмма последовательности: Генерация задачи

```
Closure Worker -> Closure Worker: Wake up (5s interval)
Closure Worker -> PostgreSQL: UC-9: Find closable clusters
PostgreSQL -> Closure Worker: Return batch(10) FOR UPDATE SKIP LOCKED
loop for each cluster
    Closure Worker -> PostgreSQL: UC-10: Set status=processing
    Closure Worker -> PostgreSQL: UC-11: Get cluster events
    PostgreSQL -> Closure Worker: Return events sorted by occurred_at
    Closure Worker -> LLM API: UC-12: Generate task
    LLM API -> Closure Worker: Return JSON task
    alt Success
        Closure Worker -> PostgreSQL: UC-13: Create task
        Closure Worker -> PostgreSQL: UC-14: Set status=closed
    else Error
        Closure Worker -> PostgreSQL: UC-15: Rollback status=open
    end
end
```
